1. 前言：为什么学了语法还不够？

很多人学 CUDA 的路径是这样的：

你背熟了 thread、warp、block、grid 的定义，写出了能跑通的 <<<grid, block>>> 调用——但性能一塌糊涂。问题不在语法，在于你没想清楚「这条指令到底跑在哪块硅片上、为什么要这么编排」。

本文用一个贯穿始终的类比来帮你建立硬件直觉：

GPU 是一家巨型餐厅的后厨。CPU 是一位米其林大厨（单打独斗、做一道是一道），GPU 是 100 个炒菜师傅同时开火。你的 kernel 就是菜谱——菜谱写不好，100 个师傅也只能排队等锅。

带着一个问题去读：为什么 GPU 不是「更快的 CPU」，而是另一种完全不同的东西？

CPU（米其林大厨） GPU（百人后厨）
厨师数量 1~16 位顶级大厨 数千位普通厨师

核心洞察：CPU 设计目标是「让一个任务尽快完成」；GPU 设计目标是「让一万个任务整体最快完成」。这是两种完全不同的哲学。

3. SM——GPU 的「后厨」

3.1 SM 是什么？

SM（Streaming Multiprocessor，流式多处理器） 是 GPU 上最小的完整计算单元。可以把它理解成餐厅里的「一个独立后厨」——里面锅碗瓢盆一应俱全，能独立完成一道菜的完整流程。

一颗 GPU 芯片上有几十到上百个 SM。以 NVIDIA A100 为例：

参数 A100 (GA100)
SM 总数 108 个（满血版 128，A100 屏蔽部分）
每个 SM 的 FP32 ALU 64 个
每个 SM 的 INT32 ALU 64 个
每个 SM 的 Tensor Core 4 个
每个 SM 的寄存器文件 65,536 个 32-bit 寄存器
每个 SM 的 Shared Memory 最大 164 KB（可配置）
每个 SM 的 L1 缓存 与 Shared Memory 共享 192 KB
每个 SM 最大线程数 2,048
每个 SM 最大 Warp 数 64
每个 SM 最大 Block 数 32

3.2 SM 内部结构图

3.3 各部件通俗解释

部件 类比 作用
Warp Scheduler（调度器） 厨房领班 决定「下一锅炒什么」，每个周期挑一个准备好的 warp 发指令
Dispatch Unit（分发器） 传菜员 把指令拆成具体操作，派发给 ALU 和内存单元
FP32 ALU 炒锅 执行浮点运算（矩阵乘法、向量加法等主力）
INT32 ALU 切菜板 执行整数运算（地址计算、循环计数器等）
Tensor Core 高压锅（专用设备） 一个周期完成 4×4 矩阵乘加运算，AI 训练/推理加速
Register File 厨师手边的备料台 每个线程的局部变量存在这里，访问最快（0 延迟）
Shared Memory 公共备料区 一个 block 内所有线程共享，比全局内存快 ~100 倍
L1 Cache 冰箱（本地） 缓存全局内存数据，减少远距离取料

关键认知：Warp Scheduler 是整个 SM 的「大脑」。它不执行运算，只负责决策——在几十个等待中的 warp 里选出「已经准备好的」那个，把它的下一条指令发出去。这个决策每个时钟周期都在发生。

4. 线程怎么跑到硬件上？——Thread → Warp → Block → SM

4.1 映射层次图

4.2 三条铁律

铁律 1：一个 Block 一旦被分配到某个 SM，就永远锁死在那里，不会被迁移。
→ 这就是 Shared Memory 只在 Block 内共享的硬件根源——因为数据就在那个 SM 上。

铁律 2：Warp 的分组按 threadIdx 升序自动完成，程序员没有任何控制权。
→ 连续的 32 个 threadIdx.x（然后 y，再 z）自动形成一个 warp。你必须让数据布局和这 32 个线程的访问模式对齐。

铁律 3：Block 不跨 SM，但 Grid 的不同 Block 可以在不同 SM 上真正并行执行。
→ 这是 GPU 能跑满几千个核的基础——每个 SM 领走几个 Block，各自独立干活。

6. Warp Divergence——隐形的性能杀手

⚠️ 原文重大遗漏纠正：原文对 divergence 的讨论基于传统的 SIMT 模型（warp 内所有线程完全锁步，分支串行执行两条路径）。但自 Volta 架构（2017 年）起，NVIDIA 引入了 Independent Thread Scheduling（ITS）——warp 内每个线程可以有独立的程序计数器，不需要同时执行两个分支的全部指令。你的代码行为取决于编译目标架构（-arch=sm_70 及以上启用 ITS）。

6.1 Divergence 本质：一个 warp 的线程走了不同分支

6.2 两种解决方案（附代码）

方案 1：用 Predication（条件赋值）替代跳转

编译器生成的 PTX 指令：setp.lt → selp.f32（一条 select 指令替代两个分支块）。select 是单指令，warp 内所有线程同时执行，不产生分支惩罚。

方案 2：数据重排——让同分支线程聚在同一个 warp

6.3 什么时候用哪个？

场景 推荐方案 原因
分支很短（1~3 条指令） Predication 条件赋值比跳转开销小
分支很长（10+ 条指令） 数据重排 避免大量线程被闲置
分支条件与 threadIdx/laneId 相关 优先 Predication 条件对 warp 内所有线程可预测
分支条件依赖输入数据 数据重排 根除不一致性而非掩盖

工程直觉：看到 if 条件跟 threadIdx 有直接关系 → 先停下来想想能不能换成 Predication 或重排数据。这是 GPU 调优 90% 的低垂果实。

7. Occupancy——SM 能同时招待多少 Warp？

7.1 Occupancy 是什么？

Occupancy（占用率）= 一个 SM 上当前活跃的 warp 数 ÷ SM 最大 warp 数。

直观理解：一个后厨同时管多少个灶。灶越多，空灶的概率越低——但每个灶的火力可能会变小（因为资源被摊薄了）。

7.4 ⚠️ Occupancy ≠ 性能（原文正确，但需强调）

这是初学者最容易混淆的点，我来展开说明：

判断标准（实操）：

  1. 用 nvcc --ptxas-options=-v 看编译后实际寄存器用量
  2. 用 Nsight Compute 的 Warp State Statistics 看 warp 到底在等什么
    • 如果 Stall Long Scoreboard 占比最大 → 等内存，需要提高 occupancy
    • 如果 Stall Not Selected 占比最大 → ALU 已满载，occupancy 够了
  3. 寄存器用得少（如 < 32 per thread）→ 可适当增大 block size 提 occupancy
  4. 寄存器紧（如 > 64 per thread）→ 不要为了 occupancy 硬减寄存器，register spill 到 local memory 的代价远超 occupancy 收益

9. 常见误区与纠正

误区 1：「Block size 一定要是 32 的倍数」

纠正：不绝对。但强烈建议 ≥ 128 且是 32 的倍数。

  • Block size 不是 32 倍数 → 最后一个 warp 不满 32 线程 → 那些 ALU 就浪费了
  • Block size 太小（如 32 = 1 warp）→ 要填满 SM 需要很多 block → occupancy 受限
  • 建议：128 或 256 作为起点，然后 profile 调优

误区 2：「Shared Memory 越大越好」

纠正：用了多少就扣多少「occupancy 配额」。

  • 每 block 用 48 KB → 同 SM 最多 3~4 block → occupancy 可能骤降
  • 不要为了用 Shared Memory 而用——确认有数据复用或 bank conflict 优化需求再用
  • 有时不用 Shared Memory、让 L1 自动缓存，反而 occupancy 更高、整体更快

误区 3：「无脑追求 100% Occupancy」

纠正：这是最常见的 tuning 误区，已在 7.4 节详细说明。

一句话口诀：compute-bound 不用追，memory-bound 追不够。

误区 4：「让 threadIdx.x 访问连续地址只是经验法则」

纠正：这是硬件合并访问（Coalesced Access）的必然要求。

误区 5：「多开 block 总比少开好」

纠正：block 太多可能阻塞 SM 上的资源。

  • 每个 SM 最多同时 32 个 block
  • 超出部分在硬件调度器里排队（不占 SM 资源但也不执行）
  • Grid 维度建议是 SM 数量的整数倍，保证负载均衡

10. 总结：把知识串起来

回到开头的问题——GPU 不是更快的 CPU，它是另一种东西。

GPU 做出的每一个设计选择，都指向同一件事：用并行度换延迟容忍。

现在那些「最佳实践」不再是死记硬背了：

实践 硬件根因
threadIdx.x 连续访问连续地址 32 lanes 一次 128B cache line → 合并成一次内存事务
block size 是 32 的倍数 不满的 warp 会浪费整个 warp 调度槽位
Shared Memory 避免 bank conflict 32 banks 对应 32 lanes，冲突就串行
不无脑追 100% occupancy 减寄存器换 warp 数往往得不偿失（register spill）
用 predication 替代短分支 避免 warp divergence 导致的串行执行

11.4 练手建议

把一个矩阵乘法从 naive 实现写到接近 cuBLAS 的性能，比读十篇综述都有用。

练习路径：

  1. naive：每个线程算一个输出元素 → 搞清楚 grid/block 划分
  2. + coalesced access：让 threadIdx.x 连续 → 理解内存合并
  3. + shared memory tiling：每个 block 把一小块矩阵搬进 SMEM → 理解数据复用
  4. + double buffering：边算边加载下一块 → 理解异步与延迟隐藏
  5. + vectorized loads：用 float4 一次读 16 字节 → 理解内存带宽利用率
  6. profile 对比每一步：Nsight Compute 看 stall 原因的变化
